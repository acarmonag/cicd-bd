C2 · Modelos Gold y lógica de negocioMiguel · 3 min

Dos modelos, dos preguntas de negocio

fct_rendimiento_equipos

¿Cómo va cada equipo en la tabla de posiciones de su torneo?

  • Grano: una fila por (equipo, torneo).
  • Fuentes: 100% relacionales — stg_matches, stg_match_scores, stg_teams, stg_tournaments.
  • Puntos, victorias, empates, diferencia de gol y row_number() para la posición.

fct_recaudo_por_partido — cruza 2 orígenes

¿Cuánto recaudó cada partido en taquilla, y cuántas boletas se vendieron por categoría?

  • Grano: una fila por (partido, categoría de boleta).
  • stg_ventas_tickets (JSON, TicketAndes) + stg_matches / stg_teams (relacional, Neon).
  • Unidos por match_id — el proveedor externo ya lo conocía.

El grano de ambos no es una promesa: cada uno tiene un test dbt_utils.unique_combination_of_columns que lo prueba.

Notas del ponente — Miguel El primero, fct_rendimiento_equipos, es la tabla de posiciones: una fila por equipo y torneo, con puntos, diferencia de gol y la posición calculada con row_number(). Responde una pregunta 100% deportiva y usa solo fuentes relacionales. El segundo cruza dos orígenes de datos distintos del propio proyecto — requisito explícito de este momento: fct_recaudo_por_partido une las boletas de TicketAndes, que vienen del JSON aplanado en el Momento 2, con los partidos y equipos que vienen de Neon. El punto de unión es el match_id, que el proveedor externo ya conocía porque el organizador registra el partido en su plataforma al abrir la venta. Responde: ¿cuánto recaudó cada partido en taquilla, y cuántas boletas se vendieron por categoría? En ambos modelos, el grano no es una promesa: está probado con un test de combinación única.
C3 · Pruebas de calidad de datosMiguel · cierra

Genéricos para integridad,
dbt-expectations para negocio

  • unique + not_null en cada llave primaria de Silver y Gold.
  • relationships en cada llave foránea — incluida boleta → partido.
  • accepted_values en status, formato, categoria.
  • unique_combination_of_columns asegurando el grano de los dos Gold.

Esto solo dice que las llaves no se rompen — no que los números tengan sentido de negocio. Para eso, dos tests de dbt-expectations.

2 tests dbt-expectations, con razón de negocio

TestReglaPor qué
expect_column_values_to_be_betweenprecio_usd 0–500>500 = total de orden mal tipado como precio de boleta
expect_table_row_count_to_be_between1–5000 filas19 partidos: 0 = ingesta caída, >5000 = archivo duplicado
Notas del ponente — Miguel Sobre integridad estructural tenemos lo esperado: unique y not_null en cada llave primaria, relationships en cada llave foránea —incluida la boleta contra el partido— y accepted_values en los campos de estado y categoría. Pero eso solo dice que las llaves no se rompen, no que los números tengan sentido de negocio. Por eso agregamos dos tests de dbt-expectations, cada uno con una razón de negocio detrás, no porque el paquete lo permita. El precio de una boleta tiene que estar entre 0 y 500 dólares — si aparece más, es casi seguro que el export mezcló el total de la orden con el precio de una sola boleta. Y el conteo de filas de boletas tiene que estar entre 1 y 5000 — nuestro torneo tiene 19 partidos: cero boletas es la ingesta JSON fallando por completo, y más de 5000 es el mismo archivo cargado dos veces sin limpiar la tabla. Con esto le paso la palabra a Andrés para la automatización y la demo en vivo.
C4 · Automatización con GitHub ActionsAndrés · abre

Un commit en dbt/ dispara dbt build

on:
  push: {branches: [main, dev], paths: ["dbt/**"]}
  workflow_dispatch:
  schedule: [{cron: "0 7 * * *"}]  # tras el ELT + JSON

# dbt build = dbt run + dbt test, en orden del DAG.
# Si un test Silver falla, los Gold ni se intentan.
uv sync --locked
cp profiles.yml.example profiles.yml
uv run dbt deps --profiles-dir .
uv run dbt build --profiles-dir . --target dev
  • Credenciales de Snowflake como Secrets de GitHub — nunca en el repositorio.
  • profiles.yml.example es la plantilla; los valores llegan por env_var().
  • concurrency serializa runs — dos ejecuciones no se pisan a mitad de escritura.

Y ahora se los mostramos corriendo de verdad, no en una diapositiva.

Notas del ponente — Andrés Ahora el turno técnico. Este workflow, dbt_build.yml, se dispara solo con cualquier cambio dentro de la carpeta dbt/, además de poder correrse manualmente o por cron todos los días a las 7am UTC. Instala el entorno con uv, resuelve los paquetes con dbt deps, y corre dbt build — que es dbt run más dbt test respetando el orden del grafo: si un test de un modelo Silver falla, los modelos Gold que dependen de él ni se intentan. Las credenciales de Snowflake viven como Secrets de GitHub, nunca en el repositorio — el runner arranca desde profiles.yml.example y las inyecta con env_var(). Y ahora se los muestro corriendo de verdad, no en una diapositiva.

RetrospectivaAntonio · 3 min

Qué costó, qué haríamos distinto,
qué queda pendiente

Lo más difícil

No fue el SQL de los Gold: fue la automatización. DBT_PROJECT_DIR colisiona con una variable que dbt-core ya reconoce como --project-dir y la resuelve dos veces junto con working-directory — el runner fallaba con un path inexistente. Y el setup de Snowflake necesitó ACCOUNTADMIN: el rol de servicio del Momento 2 no alcanzaba para todo lo que dbt necesita crear.

Qué haríamos distinto

Escribir los tests de dbt-expectations junto con cada modelo Gold, no después — pensamos los límites de negocio (los 500 dólares, las 5000 filas) más tarde de lo que debimos.

Fuera de alcance a propósito

No es lo que falta: es lo que el propio módulo dejó fuera porque no se enseñó en este capítulo.

  • Modelos incrementales
  • Capa de entrega / dashboard (Streamlit)
  • Orquestadores externos (Airflow, Dagster)
  • Streaming / tiempo real

La conversación natural para seguir, una vez el batch es confiable.

Notas del ponente — Antonio Para cerrar, la retrospectiva. Lo más difícil no fue el SQL de los modelos Gold — fue el detalle de la automatización. Documentamos en el propio workflow un error real que nos costó tiempo: si la variable de entorno del proyecto se llama DBT_PROJECT_DIR, dbt-core la reconoce como equivalente a --project-dir y, combinada con working-directory en el step, la resuelve dos veces y el runner falla con un path que no existe. Tuvimos que renombrarla. Y en el setup de Snowflake corregimos el rol con el que se crean los objetos base a ACCOUNTADMIN, porque el rol de servicio del Momento 2 no alcanzaba para todo lo que dbt necesita crear. Si lo hiciéramos de nuevo, escribiríamos los tests de dbt-expectations al mismo tiempo que cada modelo Gold, no después. Y queda pendiente todo lo que el propio módulo dejó fuera a propósito: modelos incrementales, una capa de entrega o dashboard, orquestadores externos como Airflow, y streaming. No lo evaluamos porque no se enseñó en este capítulo — pero es la conversación natural para seguir, una vez el pipeline batch ya es confiable.

¿Cuál es el camino, y cuánto tarda?

Push a dbt/ → GitHub Actions dispara dbt build → modelos y tests corren en orden del DAG → tabla actualizada en Snowflake, en minutos, sin pasos manuales.
