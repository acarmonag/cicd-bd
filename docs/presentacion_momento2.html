El encargo

La liga ya opera en Neon.
El análisis no puede vivir ahí.

El Momento 1 dejó la base transaccional del torneo versionada con Flyway y desplegada por CI/CD. Pero las queries analíticas pesadas degradan el sistema operacional — y no todo dato del negocio vive en esa base: la venta de boletas ocurre en la plataforma de un tercero.

El encargo: construir ambos caminos de ingesta hacia Snowflake y dejar el resultado operable y protegido.

Las 4 preguntas que respondemos hoy

  • ¿Cómo llegan los datos de Neon a Snowflake, y quién ejecuta ese proceso?
  • ¿Qué pasa si la fuente relacional cambia de esquema sin avisar?
  • ¿Cómo entra un dato sin esquema fijo, y qué se hace con él?
  • ¿Quién puede ver qué, y por qué no "todos ven todo"?

E3 · Schema drift — caso provocado y corregido

Backend agregó attendance sin avisar.
El pipeline lo contó antes de romperse.

-- el "backend" (nosotros), directo en Neon dev:
ALTER TABLE matches ADD COLUMN attendance INTEGER;

$ uv run elt_neon_to_snowflake.py --tabla matches
ERROR:
Schema drift detectado en MATCHES: la fuente en Neon
trae columna(s) nueva(s) que Snowflake no tiene
todavía: ['ATTENDANCE'].

Aplica esto en un Worksheet y vuelve a correr:
ALTER TABLE MATCHES ADD COLUMN "ATTENDANCE" FLOAT;
  • La comparación (DataFrame vs. information_schema.columns) corre antes de write_pandas: Snowflake nunca se tocó.
  • Mensaje accionable: tabla, columna y el DDL de roll-forward ya redactado — no un invalid identifier críptico tres capas abajo.
  • El DDL se muestra, no se auto-ejecuta: alterar el warehouse sin revisión es su propio riesgo.
  • Aplicado el ALTER, la re-corrida cargó 19 filas sin tocar una línea de código.

Mismo criterio que Flyway en el Momento 1: detectar antes de fallar. ¿Por qué FLOAT? Los partidos no jugados traen NULL y pandas representa enteros anulables como float64 — el tipado fino es de capas posteriores.

E4 · La segunda fuente

TicketAndes: la boletería vive
fuera de nuestro sistema

Exports semanales del proveedor de ticketing — órdenes de compra de boletas para los partidos. No existe en el modelo relacional del Momento 1: es el proceso de un tercero.

  • Array anidado tickets: una orden compra 1–4 boletas → la pregunta de negocio se responde por boleta.
  • Claves que no siempre vienen: buyer.phone (~⅓ no lo da), section (palcos), installments (solo tarjeta).
  • Un proveedor externo no negocia su esquema contigo → schema-on-read.

E4 · External Stage + VARIANT

Schema-on-read: el JSON aterriza
sin esquema previo

CREATE FILE FORMAT FF_TICKETING_JSON
  TYPE = JSON  STRIP_OUTER_ARRAY = TRUE;  -- [ {…}, {…} ]

CREATE STAGE STG_TICKETING_S3
  URL = 's3://s3-tournamet-test-eafit/'
  FILE_FORMAT = FF_TICKETING_JSON;    -- referencia, no copia

COPY INTO RAW_TICKETING (RAW_DATA, ARCHIVO)
FROM (SELECT $1, METADATA$FILENAME FROM @STG_TICKETING_S3)
PATTERN = '.*ticketing_export_.*[.]json'
FILE_FORMAT = (FORMAT_NAME = FF_TICKETING_JSON);
  • LIST @stage y SELECT $1 exploran antes de cargar — sin mover nada.
  • Tabla de una sola columna VARIANT + metadatos de auditoría (ARCHIVO, CARGADO_EN).
  • COPY INTO es idempotente: re-ejecutado carga 0 filas — por eso puede correr a diario.

Herida de guerra (real)

El bucket compartido tenía un PDF ajeno; el primer COPY murió con “Error parsing JSON… .pdf”. El PATTERN no es adorno: es parte del contrato de ingesta.

E4 · LATERAL FLATTEN

28 órdenes → 74 boletas

SELECT
  RAW_DATA:order_id::STRING        AS ORDER_ID,
  RAW_DATA:buyer.email::STRING     AS COMPRADOR_EMAIL,
  boleta.value:section::STRING     AS SECCION,  -- NULL en palcos
  boleta.value:price_usd::FLOAT    AS PRECIO_USD
FROM RAW_TICKETING,
     LATERAL FLATTEN(input => RAW_DATA:tickets) boleta;
-- materializado en STAGING.STG_VENTAS_TICKETS
PartidoBoletasRecaudo USDSin sección
LMF2026-M14191 27614
LMF2026-M15221 0086

FLATTEN es un JOIN de la orden contra sus propios ítems: una orden con 4 boletas produce 4 filas. Clave ausente → NULL, nunca error: 26/74 sin sección, 40/74 con teléfono, 19/74 con cuotas.

E5 · Orquestación nativa

Un DAG de dos tareas, sin Airflow

TASK_INGESTA_TICKETINGraíz · CRON 0 5 * * * America/Bogota · COPY INTO
→ AFTER →
TASK_APLANAR_TICKETShija · sin reloj propio · INSERT OVERWRITE
  • La hija se dispara cuando la raíz termina con éxito: dependencia lógica, no coincidencia de horarios.
  • INSERT OVERWRITE y no CREATE OR REPLACE: una sentencia, conserva GRANTs y masking policies.
  • Activación de todo el grafo: SYSTEM$TASK_DEPENDENTS_ENABLE.
  • EXECUTE TASK es privilegio de cuenta — ser dueño de la task no basta.
-- TASK_HISTORY tras el disparo manual (hora Bogotá):

E5 · Administración real

Apagar un DAG tiene un orden.
No es el que uno cree.

-- intento "natural": suspender la hija primero
ALTER TASK TASK_APLANAR_TICKETS SUSPEND;
091421 (22000): Unable to update graph with root task
TASK_INGESTA_TICKETING since that root task
is not suspended.

-- orden correcto: la raíz primero, siempre
ALTER TASK TASK_INGESTA_TICKETING SUSPEND;  -- OK
ALTER TASK TASK_APLANAR_TICKETS   SUSPEND;  -- OK
  • El error es real, de nuestra cuenta — no teoría de la documentación.
  • Mientras la raíz siga started, el grafo está "en juego": nada del DAG se puede alterar.
  • Activar no tiene esa restricción: TASK_DEPENDENTS_ENABLE resuelve el orden solo.
  • TASK_HISTORY() es la primera parada para depurar — aquí no hay logs de aplicación.

Las tasks quedan suspendidas entre demos para no quemar crédito del trial — el warehouse XSMALL con auto-suspend hace el resto.

E6 · RBAC

Quién ve qué — porque lo necesita,
no porque puede

Nadie de negocio entra a RAW_JSON: el VARIANT crudo contiene la PII sin enmascarar — abrirlo dejaría la política pintada en la pared.

USE ROLE ROLE_GERENCIA_COMERCIAL;
USE SECONDARY ROLES NONE;
SELECT * FROM TORNEOS_DB.RAW.PLAYERS;
-> Schema 'TORNEOS_DB.RAW' does not exist
   or not authorized.

Hallazgo propio

Los usuarios del trial nacen con DEFAULT_SECONDARY_ROLES=('ALL'): la sesión suma los privilegios de todos tus roles y el SELECT "prohibido" pasa igual. La demo honesta exige USE SECONDARY ROLES NONE. El masking no depende de esto: evalúa CURRENT_ROLE(), el rol primario.

E6 · Dynamic Data Masking — en vivo (Enterprise)

El mismo SELECT.
Tres roles, tres verdades.

SELECT COMPRADOR_NOMBRE, COMPRADOR_EMAIL, COMPRADOR_TELEFONO FROM STG_VENTAS_TICKETS WHERE COMPRADOR_TELEFONO IS NOT NULL;

-- ROLE_GERENCIA_COMERCIAL (dueña del dato de cliente)
Isabela Franco | isabela.franco@hotmail.com | +57 302 815 2965

-- ROLE_ANALISTA_DEPORTIVO (analiza demanda, no identidades)
Isabela Franco | *****@hotmail.com          | +57 302 *** ****

-- ACCOUNTADMIN (administrar la cuenta no es motivo para ver PII)
Isabela Franco | ********                   | *** *** ****

La política se evalúa al vuelo en el plan de cada query — no hay una segunda tabla enmascarada. Se ata una vez a la columna (MASK_EMAIL, MASK_TELEFONO) y todo consumidor futuro hereda la protección.

El analista conserva dominio y prefijo — le sirven para analizar canales — y pierde la identidad. NULL entra, NULL sale: la política no inventa datos.

Cierre

Las 4 preguntas, respondidas
con evidencia

¿Cómo llegan los datos, y quién ejecuta?

ELT en Python con uv, carga masiva con write_pandas, conectado como TORNEOS_LOADER — nunca ACCOUNTADMIN.

¿Y si el esquema cambia sin avisar?

El drift se detecta antes de cargar, con el ALTER TABLE de roll-forward ya redactado. Caso provocado y corregido.

¿Cómo entra el dato sin esquema fijo?

External Stage → VARIANT → LATERAL FLATTEN → STG_VENTAS_TICKETS, refrescado por un DAG de Tasks nativo.

¿Quién puede ver qué?

Dos roles de negocio con GRANTs deliberados y masking dinámico: el mismo SELECT devuelve tres resultados según el rol.
